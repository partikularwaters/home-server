Hidden Is Not Protected

Why you can't trust anything that comes from the browser.

Eric Acosta · John Madrid

The model

Two computers

Theirs

The browser. The user's machine. They can read and change everything in it.

Ours

The server. Our machine. The only place a rule can actually be enforced.

The browser sends claims. The server decides what's true.

What the user controls

Everything in the browser is editable

  • HTML — view source, change any text, price, or label.
  • CSS — un-hide anything marked "hidden".
  • JavaScript — pause it, rewrite it, skip it.
  • DevTools — edit a form field, replay a request with new values.

"Hidden" in the browser means "one right-click away".

Case file

A real checkout hack

  • September 2026: a bug-bounty researcher intercepted a checkout request, changed the amount field, and the server accepted it — without ever re-checking the invoice.
  • The price check lived only in the browser. The server trusted the claim.
  • OWASP lists exactly this under Web Security Testing Guide: Test Payment Functionality — tamper hidden fields, replay modified requests.
Bias note: the writeup comes from a bounty hunter, who is paid to find and dramatize impact; the target's name is redacted for responsible disclosure. OWASP is a vendor-neutral community standard — drier, and the stronger citation.
Live demo

HomeServer

A small parts store. Checkout has one control the customers never see: a Hidden / Protected toggle.

  • Hidden: the order goes to a table that trusts the browser's total.
  • Protected: the order goes to a table where the database re-checks the price before writing anything.

We'll change the total in DevTools, submit, and then ask the server what it actually stored.

The takeaway

Hidden is not protected.

For any feature, price, or permission, ask two questions:

  • Does the browser enforce it? → cosmetic.
  • Does the server re-check it? → real.
